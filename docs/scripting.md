# Сценарии в командной строке (план)

Командная строка стратегии остаётся аргументами движка с `# комментариями` и ссылками `{…}`;
строки, начинающиеся с `@`, — директивы, которые выполняет приложение. Движок по-прежнему
получает обычные аргументы. На директивах можно собрать свой подбор стратегий и автоподбор;
встроенные «Подбор стратегий» и «Автоподбор» со временем станут готовыми сценариями.

Статус: этапы 1 (0.21.0) и 2 (0.21.0: `@sites`/`@for`/`@try`/`@fallback`, слоты движка) реализованы, этап 3 (`@on`, 0.22.0) реализован; `@scenario` — в работе. `@restart …` принимается, но при слотах смена варианта перезапуска не требует.

## Сети

Сеть различается только по типу: `wifi` или `mobile` (без имени Wi-Fi: на Android 10+ для него
нужно разрешение на местоположение). Результаты подбора запоминаются отдельно для каждого типа.

## Этап 1. Статический слой (без проверок)

```
@set sni = www.google.com              # переменная, дальше $sni
@include "Discord termux"              # стратегия из «Моих стратегий»
@block YouTube                         # именованный блок: переключатель в интерфейсе
  --hosts {list:youtube} -C {proxy:termux} --auto=none
@end
@if mobile                             # wifi | mobile
  --tlsrec 1+s
@end
```

Рядом с редактором — вкладка «итоговая команда»: что получит движок в текущей сети; ошибки с
номером строки, как в редакторе настроек.

## Этап 2. Подбор и перезапуск

```
@sites discord = discord.com gateway.discord.gg cdn.discordapp.com
@for discord
@try
  --disorder 1
@or
  --oob 3
@or
  -C {proxy:termux}
@end
```

`@try` проверяет варианты тестовым движком вне VPN (как автоподбор), берёт первый, который
загрузил все сайты, и даёт движку `--hosts <список> <победитель> --auto=none`. VPN стартует с
последним удачным вариантом для этой сети, подбор идёт в фоне.

`@fallback … @or … @end` — без проверки заранее: группы `--auto=torst,ssl_err` движка, который
сам переходит к следующему варианту при блокировке.

Перезапуск движка, когда фоновый подбор нашёл вариант лучше:

```
@restart ask              # auto | ask | never (по умолчанию ask)
@restart-delay 10s        # собрать находки пачкой
@restart-idle 30s         # только если нет передачи N секунд
@restart-limit 3/h        # не чаще; сверх — спросить
@restart-keep udp         # не рвать идущие UDP-потоки (звонки)
```

У блока можно переопределить: `@end restart=auto`.

## Этап 3. Реакции на события журнала

```
@on <причина> [<домены/маска>] [tcp|udp] [<порог>] -> <действие>
```

Причины (из журнала соединений движка): `block` (сброс, редирект, ошибка TLS), `freeze`
(зависание на 16–20 КБ), `noreply` (нет ответа на TLS), `connfail` (нет TCP-соединения),
`udp-noreply` (UDP без ответа), `proxy-down` (прокси отказывает), `any`.

Действия: `try { … | … }`, `use <аргументы>`, `proxy <имя>`, `autofix`, `notify`, `ignore`.

Порог: `x3/5m` — 3 раза за 5 минут.

```
@restart auto
@restart-idle 20s
@on freeze *.discord.com,discord.gg tcp -> proxy termux
@on noreply *.youtube.com,*.googlevideo.com x2/1m -> try { --disorder 1 | --oob 3 | -C {proxy:termux} }
@on udp-noreply {ipset:telegram} udp -> use --udp-fake 6 --ttl 4
@on proxy-down -> notify
@on any x3/10m -> autofix
@on any *.doubleclick.net,mc.yandex.ru -> ignore
```

Приложение читает журнал текущей сессии, при совпадении (причина, домен, протокол, порог)
выполняет действие; найденное решение становится правилом «домен → стратегия» и применяется по
`@restart`. Срабатывания видны в журнале и на экране мониторинга.

## Этап 3б. Сценарии: применить → проверить → повторить → эскалация

Автомат состояний на домен (группу доменов): событие → `apply` → `verify` → удовлетворительно:
спать и следить; нет: `retry`; попытки кончились: `escalate` по очереди; всё неудачно: `fail`.

```
@on noreply,freeze *.youtube.com,*.googlevideo.com tcp -> run youtube

@scenario youtube
  apply   --disorder 1 --tlsrec 1+s
  verify  loaded within 20s
  retry   3 every 30s
  escalate try { --oob 3 | --disoob 1 | -C {proxy:termux} }
  escalate autofix
  fail    notify, cooldown 30m
  ok      watch
@end
```

Условия `verify` (можно сочетать через `and`): `loaded` (проверка загрузила без зависания),
`responded` (сервер ответил), `quiet 2m` (в журнале нет сбоев по доменам), `bytes>64k`
(реальные соединения получают больше), `udp-reply` (UDP-поток получил ответ), `latency<2s`.

`apply … for 10m` — временно: по истечении вернуть как было и снова проверить.

Встроенные защиты: общий лимит попыток в час, минимальная пауза между циклами, одна проверка за
раз на домен. Каждый шаг пишется в журнал и виден в мониторе. Перезапуск движка — по `@restart`.

## Основа этапов 2–3: смена стратегии домена без перезапуска движка

Движок читает аргументы один раз при старте, поэтому сейчас другая стратегия для домена — это
перезапуск. План доработки движка:

1. **Слоты.** При старте движок получает группы для всех стратегий, что встречаются в сценарии
   (варианты `@try`, `apply`, `escalate`, прокси `-C`); у каждой — свой пустой динамический
   список доменов. Параметры разобраны один раз.
2. **Канал управления.** Команды приложения во время работы: `assign <домен> -> <слот>` /
   `assign <домен> -> none`. Движок переносит домен между списками (деревья поиска — вставка и
   удаление дешёвые). Движок однопоточный: команда приходит через внутренний канал, который будит
   цикл событий, — без гонок.
3. **Соединения.** Новые соединения к домену сразу идут новой стратегией (группа выбирается при
   подключении по имени); открытые не рвутся — обход применяется к первым пакетам, они доживают
   со старыми параметрами. UDP — так же, по новым потокам.
4. **Перезапуск остаётся** только при изменении текста сценария или когда нужна стратегия вне
   заранее загруженных слотов (например, найденная `autofix`) — тогда по `@restart`. Добавление
   слота на лету — отдельный, более поздний шаг.
