# zapret-termux

Обход DPI на Android **без root** с помощью [zapret](https://github.com/bol-van/zapret) (tpws) в Termux + proot-distro.
Работает и для TCP (сайты, YouTube, Discord), и для **UDP** (QUIC/HTTP3, голос Discord, STUN), благодаря собственному патчу tpws.

> Это отдельный проект в ветке [`termux-zapret-udp-script`](https://github.com/k0kfjjfkdjf/zapret_android-port_claude/tree/termux-zapret-udp-script). Android-приложение ZapretDroid живёт в основной ветке этого же репозитория. Это два разных подхода к одной задаче.

## Как это работает

```
Приложения (YouTube, Discord, браузер)
        │  весь их трафик
        ▼
VPN-клиент без root (SocksTun / hev-socks5-tunnel)
        │  SOCKS5: TCP CONNECT и UDP ASSOCIATE
        ▼
tpws на 127.0.0.1:1080  ── Termux + proot-distro (Ubuntu)
        │  TCP: разрезает ClientHello/HTTP-запрос (split, disorder, oob, tlsrec)
        │  UDP: перед первыми пакетами шлёт фейки с низким TTL
        ▼
Интернет (обычные сокеты, без root)
```

- **tpws** — прозрачный прокси из zapret. В режиме `--socks` он работает как обычный SOCKS-сервер, а права root ему не нужны.
- **VPN-клиент** перехватывает трафик выбранных приложений и отдаёт его в tpws. Сам Termux в VPN попадать не должен, иначе трафик tpws уйдёт по кругу.
- **UDP без root.** Разрезать UDP-датаграмму, как TCP-поток, нельзя: получатель увидит две испорченные датаграммы. Поэтому для UDP используется другой приём. Перед настоящими пакетами tpws отправляет фейковые с низким TTL (`setsockopt(IP_TTL)` доступен без привилегий). DPI видит фейк, а до сервера он не доходит.

## Что понадобится

- Android, root не нужен.
- [Termux](https://f-droid.org/packages/com.termux/) и в нём `proot-distro` с Ubuntu (Debian, Arch и Alpine тоже поддерживаются скриптом).
- VPN-клиент, который умеет SOCKS5 **с UDP ASSOCIATE** и исключение приложений. Проверен [SocksTun](https://f-droid.org/packages/hev.sockstun). Подойдут v2rayNG и NekoBox (Xray / sing-box). Клиенты на `tun2socks + udpgw` (например, SocksDroid) **не подойдут** для UDP.

## Установка

В Termux:

```sh
pkg install proot-distro
proot-distro install ubuntu
proot-distro login ubuntu
```

Внутри Ubuntu (вы root, sudo не нужен):

```sh
apt update && apt install -y curl
sh -c "$(curl -fsSL https://raw.githubusercontent.com/k0kfjjfkdjf/zapret_android-port_claude/termux-zapret-udp-script/termux/install.sh)"
zapret start
```

Установщик:

1. ставит `git`, `curl` и `ca-certificates`;
2. клонирует **только папку `termux/`** этого репозитория в `/opt/zapret-termux`;
3. запускает `zapret install`: скачивает zapret в `/opt/zapret`, накладывает патч, собирает tpws (1–3 минуты на телефоне), создаёт команду `zapret` (`/usr/local/bin/zapret` → `/opt/zapret-termux/termux/zapret`).

Переменные установщика:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `ZT_BRANCH` | `termux-zapret-udp-script` | ставить из другой ветки (например, тестовой) |
| `ZT_REPO` | этот репозиторий | ставить из форка |
| `ZT_DEST` | `/opt/zapret-termux` | куда клонировать |

Если раньше стоял старый однофайловый скрипт `zapret`, установщик заменит его. Настройки (`~/.zapret_*`) сохранятся.

**Автозапуск:** `zapret autostart on` добавит запуск в `~/.bashrc` внутри Ubuntu. zapret будет подниматься при входе в `proot-distro login ubuntu`.

## Настройка SocksTun

| Параметр | Значение |
|---|---|
| Socks Address / Port | `127.0.0.1` / `1080` (или ваш порт из `zapret status`) |
| UDP relay over TCP | **выключить**: это протокол hev-socks5-server, tpws его не понимает |
| Socks UDP Address | пусто |
| Remote DNS | можно включить: домены в UDP-пакетах tpws разрешит сам |
| Global | **выключить**. Режим per-App, отметить нужные приложения, **Termux не отмечать** |

В режиме Global SocksTun исключает из VPN только себя. Тогда исходящий трафик tpws из Termux снова попадает в VPN и уходит в петлю.

## TCP-стратегии

Стратегия — это набор параметров tpws, например `--filter-tcp=80,443 --split-pos=1,midsld --disorder`.
Стандартный набор лежит в [`data/strategies.txt`](data/strategies.txt) в формате `имя|параметры`. Ваши стратегии хранятся в `~/.zapret_strategies`. При обновлении новые стратегии из `data/strategies.txt` добавляются туда автоматически, ваши не перезаписываются.

Основные приёмы tpws:

| Параметр | Смысл |
|---|---|
| `--split-pos=1,midsld,sniext+1,…` | разрезать запрос на TCP-сегменты в этих местах (маркеры: `method`, `host`, `endhost`, `sld`, `midsld`, `endsld`, `sniext`) |
| `--disorder` | отправить вторую часть раньше первой |
| `--oob` | добавить out-of-band байт |
| `--tlsrec=sniext+1` | разбить ClientHello на две TLS-записи |
| `--mss=88` | заставить сервер отвечать мелкими сегментами (медленно, но иногда помогает) |
| `--hostcase`, `--methodeol` | трюки для HTTP |

Свою стратегию можно добавить через меню (пункт 5) или сохранить лучшую из `blockcheck`.

### Разные стратегии для разных сайтов: `zapret combine`

Одна команда tpws (один процесс) может применять разные параметры к разным доменам. `combine` собирает такую стратегию из уже имеющихся:

```sh
zapret combine discord=split_host_oob youtube=ultimate_universal default=oob
zapret combine example.com,site.org=oob_split3 default=discord name=my_combo
zapret combine list:my-sites.txt="--split-pos=1 --oob" default=oob
```

- Слева — кому: готовый набор доменов (`discord`, `youtube`, `telegram`, `twitch`), свои домены через запятую или `list:файл`. Поддомены учитываются сами: `youtube.com` покрывает и `www.youtube.com`.
- Справа — имя стратегии из `zapret strategies` или параметры tpws в кавычках.
- `default=` — для всего остального (последний профиль, без фильтра). Без него остальной трафик идёт без обхода DPI.
- Результат сохраняется как обычная стратегия (`combo_N` или `name=…`): `zapret strategy combo_1`. Его можно проверить в `blockcheck` наравне с другими.

Как это устроено: профили разделяются `--new`, у каждого фильтр `--hostlist-domains`. Если стратегия сама из нескольких профилей (как `ultimate_universal`), фильтр дописывается в каждый. tpws берёт первый подходящий профиль и перевыбирает его, когда из ClientHello становится известно имя сайта. Мультистратегия из `blockcheck` устроена так же, только списки она подбирает сама.

## UDP и профили

UDP нужен для QUIC (HTTP/3 у YouTube и Cloudflare), голоса Discord, звонков и STUN. Включается командой `zapret udp on`.

Профиль задаёт, к каким портам применять фейки и какие именно:

| Профиль | Порты | Фейки | Для чего |
|---|---|---|---|
| `discord` (по умолчанию) | 443, 3478, 19294–19344, 50000–65535 | по протоколу: QUIC, IP discovery Discord, STUN; TTL 4 ×6, первые 4 пакета | Discord, YouTube |
| `discord_quicfake` | те же | QUIC Initial google для всех протоколов, первые 3 пакета | как в стратегиях zapret.cfgs |
| `discord_low_ttl` | те же | TTL 2 ×8, первые 6 пакетов | если DPI близко |
| `discord_high_ttl` | те же | TTL 6 | если до DPI много хопов |
| `quic` | 443 | QUIC | только HTTP/3 |
| `all_ports` | все | по протоколу | звонки в других мессенджерах |
| `relay` | — | без фейков | только проксирование UDP |
| `custom` | свои | свои | `zapret udp-custom "..."` |

tpws сам определяет протокол по первому пакету потока (QUIC Initial, IP discovery Discord, STUN) и берёт для него свой фейк из `/opt/zapret/files/fake/`.

**Как подобрать TTL.** Фейк должен дойти до DPI провайдера, но не до сервера. Обычно подходит 3–6. Если не работает, попробуйте `discord_low_ttl` или `discord_high_ttl`.

### Случайный SNI в QUIC-фейках

По умолчанию QUIC-фейк — один и тот же файл (`quic_initial_www_google_com.bin`): DPI каждый раз видит одинаковый пакет с SNI `www.google.com`. С `udp-sni` tpws для **каждого** фейка собирает новый QUIC Initial со случайным доменом из списка:

```sh
zapret udp-sni default                  # список data/quic-sni.txt (yandex.ru, vk.com, gosuslugi.ru, …)
zapret udp-sni ~/my-sni.txt             # свой файл: домен в строке, # комментарии, формат hostlist
zapret udp-sni vk.com,ok.ru,mail.ru     # домены прямо в команде
zapret udp-sni off                      # обратно к фейку из файла профиля
```

Работает с любым UDP-профилем, где есть QUIC-фейки (`discord*`, `quic`, `all_ports`, `custom`), и заменяет только фейк для QUIC; фейки Discord и STUN не меняются. Пакет настоящий: QUIC v1 Initial 1250 байт со случайным DCID, внутри TLS 1.3 ClientHello (ALPN `h3`, x25519) с выбранным SNI, зашифрованный initial-ключами по RFC 9001 — DPI расшифровывает его так же, как настоящий, и видит разрешённый домен. Домены в списке должны быть такими, которые DPI пропускает. Проверить, что уходит: `zapret debug`, в логе строки `udp desync : 6 fake(s) size=1250 ttl=4 proto=quic sni=…`. Нужен tpws с текущим патчем (`zapret update`); `zapret info` показывает `udp_sni_supported=1`.

## Подбор стратегии: blockcheck

### Меню

`zapret blockcheck` без параметров (или пункт 16 главного меню) открывает меню подбора:

```
══════════ Подбор стратегий (blockcheck) ══════════
Что проверять:
   • Discord полный (11 адресов + большой файл)
   • список cfgs-discord.txt (до 40 записей)
Режим:            quick (ваши 28 стратегий)
TLS:              1.2 и 1.3 отдельно
Таймаут:          8 с на адрес
Лимит из списков: 40 записей с файла
Два этапа:        вкл (выборка 8 адресов, затем 5 лучших на всём списке)
Параллельно:      12 запросов curl
Проходы:          3 (лучшие 5 стратегий проверяются 3 раза, засчитывается только стабильное)
Мультистратегия:  выкл
Отладка:          компактная (curl -v только неудачных, лог tpws финалистов)
Папка отчёта:     /sdcard/Download/zapret
════════════════════════════════════════════════════
 1) Добавить набор (Discord, Discord полный, YouTube)
 2) Добавить список из /opt/zapret/ipset (hostlist / ipset)
 3) Добавить свой файл
 4) Ввести домены / IP / подсети вручную
 5) Убрать цели
 6) Режим: quick / full
 7) Версии TLS
 8) Таймаут
 9) Лимит записей из списков
10) Отладка: выкл / компактная / полная
11) Папка для отчёта и логов
12) Два этапа: размер выборки и число финалистов
13) Параллельность curl
14) Мультистратегия вкл/выкл (экспериментально)
15) Повторные проходы лучших (стабильность)
16) ▶ Запустить проверку
```

- **Цели можно смешивать**: готовые наборы, любые файлы из `/opt/zapret/ipset` (в том числе `cfgs-*.txt` после `zapret lists-update`), свой файл (можно `.gz`), домены, IP и подсети, введённые вручную.
- **Из списков** берутся домены (`*.` и `:*` убираются), IPv4, IPv6 и подсети CIDR (для подсети проверяется её первый адрес). IP проверяются без проверки сертификата: важно только, проходит ли соединение через DPI.
- **Папка отчёта**: домашняя, `/sdcard/Download/zapret` (файлы сразу видны в Android) или своя. Для `/sdcard` войдите в Ubuntu с `proot-distro login ubuntu --bind /sdcard`.
- Настройки и цели меню сохраняются между запусками (`~/.zapret_blockcheck.conf`, `~/.zapret_blockcheck_targets`).

### Командная строка

```sh
zapret blockcheck full discord                     # плюс ~75 сгенерированных комбинаций
zapret blockcheck discord-full                     # все сервисы Discord + большой файл (256 КБ)
zapret blockcheck list:discord                     # список cfgs-discord.txt (после zapret lists-update)
zapret blockcheck hostlist:my.txt limit=100        # файл из /opt/zapret/ipset, до 100 записей
zapret blockcheck file:/sdcard/Download/ips.txt    # любой файл: домены, IP, подсети
zapret blockcheck 162.159.128.233 104.16.0.0/13    # IP и подсети
zapret blockcheck tls13 timeout=5 example.com      # только TLS 1.3, таймаут 5 с
zapret blockcheck debug dir=/sdcard/Download/zapret discord   # с отладкой, отчёт в папку
zapret blockcheck full discord --apply             # сразу применить лучшую
zapret blockcheck full hostlist:big.txt limit=200 sample=10 top=5 par=8   # большой список
zapret blockcheck passes=3 top=5 discord-full      # 5 лучших проверить 3 раза
```

Параметры: `multi` — собрать [мультистратегию](#мультистратегия-экспериментально), `sample=N` — адресов в выборке первого этапа (`0` — один этап), `top=N` — финалистов, `par=N` — одновременных curl, `passes=N` — сколько раз проверять лучшие стратегии (1–9), `debug` / `debug=full` — компактная или полная отладка.

### Большие списки

Перебор всех стратегий по всем адресам быстро разрастается: 96 стратегий × 82 адреса × 2 версии TLS — это ~15 700 запросов. Поэтому:

1. **Два этапа.** Если адресов больше, чем размер выборки, сначала все стратегии проверяются на равномерной выборке (по умолчанию 8 адресов), а затем 5 лучших плюс ваша текущая стратегия — на полном списке.
2. **Не больше 12 запросов одновременно**: сотни параллельных curl перегружают и телефон, и проверяемые серверы, а это даёт ложные провалы.
3. **Компактная отладка**: подробный вывод curl сохраняется только для неудачных запросов, лог tpws — только для финалистов. Полная отладка (`debug=full`) пишет всё.
4. **Матрица результатов** `zapret-blockcheck-matrix.csv` («стратегия × адрес») — компактный итог, который удобно открыть в таблице. В ячейке `1`, если адрес открылся, иначе буква причины (см. ниже).
5. **Отчёт по адресам** `zapret-blockcheck-by-address.txt` — та же информация, развёрнутая по адресам: какие стратегии открыли адрес и почему не открыли остальные.

**Адреса не исключаются из перебора**, даже если без обхода они не открылись. Вместо исключения blockcheck:

- после проверки без обхода предупреждает, сколько адресов может быть недоступно не из-за DPI (сервер недоступен, имя не разрешилось, отказ);
- в конце перечисляет адреса, которые **не открыла ни одна стратегия**, с причиной из проверки без обхода.

```
Не открыла ни одна стратегия (2):
   http://198.51.100.99/                  без обхода: таймаут TCP-подключения (блокировка по IP?)
   https://nonexistent.invalid/ [TLS1.2]  без обхода: сервер недоступен: имя не разрешилось или нет TCP-подключения
```

### Коды причин и отчёт по адресам

В строках проверки и в матрице каждый адрес обозначен одним символом:

| Код | Что случилось |
|---|---|
| `+` (`1` в матрице) | открылся |
| `r` | сброс или обрыв TLS/соединения (типично для DPI) |
| `t` | таймаут TLS-рукопожатия (тоже типично для DPI) |
| `f` | данные перестали идти: «заморозка», большой файл не докачан |
| `c` | нет TCP-подключения или отказ (блокировка по IP?) |
| `d` | DNS: имя не разрешилось |
| `m` | подмена сертификата |
| `x` | прочее |

```
[  2/29] oob                    3/6 +++rrc  0.01s
```

Отчёт по адресам, одна строка на адрес (поля через табуляцию):

```
http://198.51.100.10/   11/29   oob advanced discord split_host_oob …   r:18
http://198.51.100.13/   18/29   default simple split2 tlsrec …          r:11
http://198.51.100.99/   0/29                                            c:29
```

Здесь `11/29` значит, что адрес открыли 11 стратегий из 29 проверенных на нём, а у остальных 18 был сброс. В двухэтапном режиме на адресах вне выборки проверяются только финалисты, поэтому знаменатель у них меньше.

### Повторные проходы

DPI иногда пропускает соединение через раз, и одна удачная проверка ничего не гарантирует. С `passes=N` (пункт 15 меню) лучшие `top` стратегий после основного подбора проверяются на полном списке ещё `N-1` раз. Адрес засчитывается, только если он открылся **во всех проходах**, и по этому стабильному числу стратегии сортируются:

```
Стабильность за 3 прохода(ов): адрес засчитан, если открылся каждый раз.
  split_host_oob         стабильно 20/22, всего успехов 64/66
  oob_split3             стабильно 18/22, всего успехов 63/66
```

В отчёте по адресам нестабильные успехи помечаются как `имя(2/3)`, а в причинах как `u:N`. Время проверки растёт примерно на `top × (N-1)` прогонов полного списка.

### Как это работает

1. Каждая стратегия запускается **во втором tpws на свободном порту**: основной zapret продолжает работать.
2. Через неё curl открывает адреса. HTTPS проверяется отдельно с **TLS 1.2 и TLS 1.3**: DPI часто режет только одну версию (в отчёте это узор `+-+-+-`).
3. Сначала адреса проверяются **без обхода DPI**: через tpws без стратегии, то есть тем же путём и с тем же DNS, что и стратегии (DNS внутри proot, часто пустой `/etc/resolv.conf`, на результат не влияет). Показывается, **на каком этапе** оборвалось соединение:
   - **DNS: имя не разрешилось** — это не DPI. Проверьте DNS в proot (см. [Если что-то не работает](#если-что-то-не-работает));
   - **таймаут TCP-подключения** — блокировка по IP, tpws её не обходит;
   - **таймаут TLS-рукопожатия / обрыв TLS** — типичный признак DPI, стратегии могут помочь;
   - **данные перестали идти** — «заморозка» DPI после начала передачи;
   - **подмена сертификата** — провайдер вмешивается в HTTPS.
4. Перед проверкой скрипт смотрит, работает ли DNS (`/etc/resolv.conf`, время разрешения имени), и предупреждает, если нет.
5. Адреса с пометкой `[256KB]` скачиваются частично (первые 256 КБ). Это ловит «заморозку» ТСПУ: соединение открывается, но после 16–20 КБ данные перестают идти. Такой адрес засчитывается, только если скачано не меньше 200 КБ. Обычная страница засчитывается, если она загрузилась целиком или если до таймаута пришло больше 64 КБ: тяжёлая страница вроде `www.youtube.com` (около 1 МБ) на медленной сети может не успеть докачаться, но данные дальше порога «заморозки» уже прошли, значит DPI её пропустил.
7. Таймаут (`timeout=N`) действует и на установку соединения вместе с TLS-рукопожатием: на медленной сети ставьте 12–15 с. Зависшее рукопожатие (`t`) отличается от отсутствия TCP-подключения (`c`) по ответу SOCKS: tpws отвечает клиенту только после того, как подключился к серверу.
6. В конце выводится топ-5 по числу открытых адресов и времени. Выбранную стратегию можно применить, сгенерированная сохраняется как `auto_N`.

Отчёт пишется в `zapret-blockcheck.log` в папке отчёта (по умолчанию `~`), рядом лежат матрица `zapret-blockcheck-matrix.csv` и отчёт по адресам `zapret-blockcheck-by-address.txt`. С отладкой появляется ещё `zapret-blockcheck-debug.tar.gz`.

### Мультистратегия (экспериментально)

Бывает, что ни одна стратегия не открывает всё: одна стратегия открывает большинство адресов, а часть адресов открывается только другой. Мультистратегия собирает из нескольких стратегий **одну команду tpws**:

```sh
zapret blockcheck multi list:discord        # или пункт 14 в меню подбора
```

1. Обычный подбор находит **основную** стратегию: ту, что открывает больше всего адресов.
2. По уже готовым результатам выясняется, какие адреса основная не открывает. Заново она проверяется, только если на полном списке её ещё не проверяли.
3. Стратегии, у которых уже есть результат на полном списке (один этап или финалисты второго), **повторно не проверяются**: их результаты берутся из подбора. Остальные проверяются **только на непокрытых адресах**. При одном этапе дополнительных проверок нет вовсе.
4. По очереди берётся стратегия, которая открывает больше всего оставшихся адресов (жадное покрытие), пока адреса не кончатся.
5. Собирается команда: сначала профили-дополнения, у каждого свой список (`--hostlist` для доменов, `--ipset` для IP), в конце основная стратегия без фильтра, она ловит всё остальное.
6. Собранная стратегия **проверяется заново** на полном списке. Если она действительно лучше основной, она сохраняется как `multi_N`, а её списки кладутся в `/opt/zapret/ipset/multi/`.

```
Мультистратегия multi_1:
  основная  oob                    (остальные адреса)
  дополнение default                +2 адр.: 198.51.100.14 198.51.100.13
  Проверок пройдено: основная 3/5 -> мультистратегия 5/5
```

Как это устроено в tpws: профили разделяются `--new` и перебираются по порядку, срабатывает первый подходящий. Если соединение пришло по IP, а имя хоста стало известно только из ClientHello (SocksTun без Remote DNS), tpws **перевыбирает профиль** по этому имени, так что фильтр по доменам работает и в этом случае. В одном профиле `--hostlist` и `--ipset` работают как «И», поэтому домены и IP идут в разные профили.

**Сборка из лога прошлого подбора** — без повторной проверки стратегий, только одна проверка собранной:

```sh
zapret blockcheck multi-from-log                         # ~/zapret-blockcheck.log
zapret blockcheck multi-from-log /sdcard/Download/zapret/zapret-blockcheck.log
```

Берутся стратегии, проверенные на полном списке (при двух этапах это финалисты). Если были повторные проходы, адрес засчитывается, только если открылся во всех. Нужен лог от версии с этой командой: в старых логах нет списка адресов.

Ограничения: стратегия привязана к адресам, на которых её подбирали. Если у сервиса сменятся IP, дополнение по `--ipset` перестанет срабатывать, и такие адреса пойдут через основную стратегию. Тогда подбор стоит повторить.

## Сбор доменов приложения: `zapret collect`

Чтобы узнать, к каким доменам и IP обращается конкретное приложение, и сделать из них hostlist:

1. В SocksTun в режиме per-App оставьте **только это приложение** (например, только Discord).
2. Запустите сбор:
   ```sh
   zapret collect discord
   ```
   zapret продолжает работать с текущей стратегией, а новые домены появляются на экране по мере подключения:
   ```
     + discord.com
     + gateway.discord.gg
     + cdn.discordapp.com
     + udp 66.22.1.2:19300 proto=discord
     + badhost.example  (ошибка)
   ```
3. Пользуйтесь приложением: разделы, звонок, видео, всё, что должно работать. Затем нажмите Ctrl+C.

Результат:

| Файл | Что внутри |
|---|---|
| `/opt/zapret/ipset/collect-discord.txt` | домены (hostlist) |
| `/opt/zapret/ipset/collect-discord-ips.txt` | IP без имени: подключения по IP, UDP-потоки, голос (ipset) |
| `~/zapret-collect-discord.txt` | отчёт: подключений и ошибок по каждому домену, его IP, UDP-потоки с временем ответа |

Повторный сбор под тем же именем **дополняет** списки. Домены, где были ошибки подключения, вынесены отдельно: это кандидаты на другую стратегию или на блокировку по IP. Имя сайта берётся и из SOCKS-запроса, и из ClientHello, так что сбор работает и с Remote DNS в SocksTun, и без него.

Дальше списки можно использовать так:

```sh
zapret blockcheck hostlist:collect-discord.txt                 # подобрать стратегию именно для них
zapret combine list:collect-discord.txt=split_host_oob default=oob   # применить стратегию только к ним
zapret hostlist-select collect-discord.txt                     # обход только для этих доменов
```

Разобрать уже готовый лог tpws (`--debug=1`, например от `zapret debug`) без нового запуска: `zapret collect discord log=~/zapret-debug.log`.

## Отладка

**`zapret debug`** запускает tpws в терминале с логом `~/zapret-debug.log`. Повторите проблему (звонок, загрузку) и нажмите Ctrl+C. В логе события идут с временем, по этапам:

```
22:40:30.940 udp flow start : -> 66.22.1.2:19300 proto=discord len=74 desync=yes fakes_before_first=6
22:40:31.942 udp discord ip discovery RETRY #1 -> 66.22.1.2:19300 after 1002ms without reply
22:40:31.992 udp flow first reply : <- 66.22.1.2:19300 after 1052ms (out=2 before reply)
22:40:32.180 socks tcp connected : c-xxx.discord.media 162.159.130.234:443 in 85ms (resolve+connect)
```

После Ctrl+C выводится отчёт:

- **UDP-потоки**: пакеты туда и обратно, `first_reply` (время до первого ответа), `fakes`. Пометка `NO REPLY` значит, что пакеты ушли, а ответа не было: их режут где-то после tpws.
- **Повторы IP discovery Discord.** Если первая датаграмма потерялась, клиент Discord ждёт около секунды и повторяет её. Отсюда долгое «Подключение…».
- **Потоки без фейков перед первой датаграммой**: порт вне профиля или UDP-десинхронизация выключена.
- **Самые медленные TCP-подключения** (разрешение имени + connect) и неудачные.

Так видно, на каком этапе тормозит: TCP (шлюз, `*.discord.media`) или UDP (IP discovery, голос).

**`zapret blockcheck debug …`** сохраняет для каждой стратегии лог tpws, подробный вывод curl по каждому адресу и сведения о системе и DNS. Всё упаковывается в `~/zapret-blockcheck-debug.tar.gz`, копия кладётся в `/sdcard/Download/`, если эта папка доступна. Этот архив удобно прикладывать к сообщению о проблеме. В нём есть IP-адреса, просмотрите его перед отправкой.

## Обычный Linux

Скрипт работает и на обычном Linux: Ubuntu, Debian, Arch, Alpine. Например, чтобы долгие подборы `blockcheck` шли на компьютере, а не нагружали телефон. Установка та же; без root установщик сам перезапустится через `sudo`:

```sh
sh -c "$(curl -fsSL https://raw.githubusercontent.com/k0kfjjfkdjf/zapret_android-port_claude/termux-zapret-udp-script/termux/install.sh)"
sudo zapret blockcheck            # меню подбора
```

Все команды запускайте через `sudo zapret …`: настройки лежат в домашней папке root, как в proot. Отчёты по умолчанию тоже попадают в `/root`; чтобы они были в вашей папке, выберите её в меню подбора (пункт 11) или укажите `dir=/home/имя/zapret`.

**Важно: DPI у каждого провайдера свой.** Стратегия, подобранная через домашний интернет, может не работать в мобильной сети и наоборот. Чтобы результат подходил телефону, подключите компьютер к интернету **через телефон**: USB-модем или точка доступа. Тогда проверка идёт через того же оператора. Некоторые тарифы ограничивают раздачу, это стоит учитывать.

Отличия от proot:

- `zapret autostart on` при наличии systemd создаёт службу `zapret-termux` вместо строки в `.bashrc`. `zapret info` показывает `platform=linux` или `platform=proot`.
- Пользоваться прокси можно и на компьютере: SOCKS5 `127.0.0.1:1080`. В Firefox: Настройки → Сеть → SOCKS v5 и «Отправлять DNS-запросы через прокси». В Chromium: `chromium --proxy-server=socks5://127.0.0.1:1080`.
- UDP через SOCKS браузеры не используют, поэтому на компьютере `blockcheck` полезен прежде всего для TCP-стратегий.

### Distrobox, podman, docker

В контейнере всё работает так же, сеть у distrobox общая с компьютером:

```sh
distrobox create --name zt --image ubuntu:24.04
distrobox enter zt
sudo apt update && sudo apt install -y curl
sh -c "$(curl -fsSL https://raw.githubusercontent.com/k0kfjjfkdjf/zapret_android-port_claude/termux-zapret-udp-script/termux/install.sh)"
sudo zapret blockcheck
```

- Внутри distrobox `sudo` работает без пароля, установщик перезапускается через него сам.
- Обычный distrobox — rootless-контейнер: в нём нет пользователя, на которого tpws по умолчанию сбрасывает права (uid 2147483647), и tpws падал бы с `setgroups: Invalid argument`. Скрипт это определяет и запускает tpws с `--uid=65534:65534` (nobody). В отладочном `sysinfo.txt` это видно в строке `uid opt`.
- Прокси из контейнера доступен на компьютере по тому же адресу `127.0.0.1:1080`.
- systemd в контейнере обычно нет, так что автозапуск для проверок не нужен: запускайте `sudo zapret start`, когда надо.

## Обновление

```sh
zapret update        # или пункт 13 в меню
```

1. `git pull` самого zapret-termux. Если пришли изменения, показывается список коммитов, и `update` **перезапускается уже новой версией**.
2. Обновляется zapret (bol-van/zapret), прошлый патч откатывается.
3. Патч из `patches/` накладывается заново, tpws пересобирается.
4. Если zapret был запущен, он запускается снова. Настройки сохраняются.

`update` следит за той веткой, из которой была установка (по умолчанию `termux-zapret-udp-script`). Если ветку переименуют, переустановите командой из раздела [Установка](#установка).

### Предыдущая версия

Версия до исправлений от 16.10.2026 (коммит `927caea`) сохранена в ветке `termux-zapret-udp-script-prev`. Откат на неё (отдельный клон, текущий `/opt/zapret-termux` не трогается):

## Если что-то не работает

| Симптом | Что проверить |
|---|---|
| `404:: command not found` при установке через curl | скачалась страница 404: не та ветка или репозиторий приватный |
| Сайты не грузятся вообще | Termux исключён из VPN? Порт в SocksTun совпадает с `zapret status`? |
| blockcheck пишет «DNS: имя не разрешилось» | в proot пустой `/etc/resolv.conf`: `echo 'nameserver 1.1.1.1' > /etc/resolv.conf` (или DNS провайдера) |
| Часть сайтов не грузится, YouTube работает | `zapret blockcheck` для этих доменов, смена стратегии |
| Сайт грузится «со скрипом» | браузер пробует QUIC: включите UDP или отключите QUIC в `chrome://flags` |
| UDP не работает совсем | в SocksTun выключен «UDP relay over TCP»? В `zapret debug` есть строки `udp flow`? |
| Голос Discord в одну сторону | профиль `discord`, затем `discord_low_ttl`; сводка `zapret debug` |
| Discord долго «подключается» к голосу | `zapret debug`: есть ли `ip discovery RETRY` и сколько `first_reply`; для проверки отключите IPv6 в SocksTun |
| После смены настроек ничего не изменилось | перезапустите VPN-клиент: он держит старые соединения |
| Ошибка сборки tpws | `zapret install` заново; при ошибке патча tpws соберётся без UDP |

## Ограничения

- **Нет фейкового TLS для TCP.** Самые сильные стратегии nfqws (fake ClientHello, `fooling=badseq`, `seqovl`) требуют сырых пакетов, то есть root. tpws умеет только разрезы и disorder. Без root фейки для TCP делает ByeDPI: он встроен в приложение ZapretDroid из основной ветки этого репозитория.
- Блокировки по IP и DNS tpws не обходит, `blockcheck` их распознаёт.
- tpws не подключается к локальным и частным адресам: это встроенная защита.
- IPv6 в UDP-патче реализован, но на реальной сети не проверялся.

## Патч tpws

[`patches/tpws-socks-udp.patch`](patches/tpws-socks-udp.patch) добавляет в tpws (режим `--socks`):

- **SOCKS5 UDP ASSOCIATE** (RFC 1928). Relay-сокет на адресе, по которому клиент подключился к tpws. Связка живёт, пока открыто TCP-соединение управления, или до таймаута простоя.
- **Фейки с низким TTL** перед первыми N датаграммами каждого потока. Отдельные фейки для QUIC Initial, IP discovery Discord и STUN.
- **Асинхронное разрешение доменов** в UDP-заголовках (ATYP=domain, режим Remote DNS в hev-socks5-tunnel). Работает через резолвер tpws, пакеты буферизуются до ответа DNS, результаты кэшируются на 5 минут.
- **Генерация QUIC-фейков со случайным SNI** (`--udp-fake-quic-sni`): для каждого фейка собирается QUIC v1 Initial (RFC 9000/9001) с TLS 1.3 ClientHello и доменом из списка, шифруется initial-ключами от случайного DCID. Используются AES-GCM и HKDF из `nfq/crypto` (патч добавляет их в `SRC_FILES` tpws), сам код — `tpws/quicfake.c`.
- **`--tlsminor`** (TCP, из ByeDPI): подменяет младший байт версии в заголовке TLS-записи с ClientHello (`16 03 XX`), в том числе во второй записи после `--tlsrec`. Часть DPI ждёт здесь стандартное значение и пропускает необычное. Серверы на OpenSSL такой ClientHello принимают; совместимость с другими серверами покажет `blockcheck full`.
- **Диагностика в логе** (`--debug=1`): события UDP-потоков с временем (`udp flow start … fakes_before_first=N`, `first reply … after Nms`, `ip discovery RETRY`, сводка `udp flow end … first_reply= fakes= NO REPLY`) и время TCP-подключений через SOCKS (`socks tcp connected … in Nms`).

Новые опции tpws:

| Опция | По умолчанию | Смысл |
|---|---|---|
| `--socks-udp` | выкл. | включить UDP ASSOCIATE (нужен `--socks`) |
| `--udp-timeout=<сек>` | 60 | таймаут простоя связки, 0 — без таймаута |
| `--udp-fake-ttl=<ttl>` / `--udp-fake-ttl6=<hops>` | — | TTL фейков; включает UDP-десинхронизацию |
| `--udp-fake-repeats=<N>` | 1 | сколько фейков перед каждым пакетом (1–100). Фейков уходит `repeats × desync-count` на поток, так что при больших значениях получается заметный всплеск пакетов |
| `--udp-desync-count=<N>` | 2 | к скольким первым пакетам потока применять |
| `--udp-desync-ports=<список>` | все | порты назначения, например `443,50000-65535` |
| `--udp-fake=<файл>` | 64 нулевых байта | фейк для неизвестного UDP |
| `--udp-fake-quic=<файл>` / `--udp-fake-discord=<файл>` / `--udp-fake-stun=<файл>` | `--udp-fake` | фейки по протоколу |
| `--udp-fake-quic-sni=<файл>\|<домены>` | — | QUIC-фейки генерируются, SNI случайный из файла или списка через запятую; можно указать несколько раз |
| `--tlsminor=<0..255>\|0xHEX` | — | байт версии в заголовке TLS-записи ClientHello (TCP) |

Из возможностей ByeDPI в tpws уже были: `--oob-data` (свой байт OOB вместо 0x00) и `--disorder --oob` (аналог `--disoob`). В режиме `blockcheck full` перебираются и они, и `--tlsminor`.

Разработка патча: склонируйте bol-van/zapret, примените патч (`git apply`), внесите изменения в `tpws/` и пересоздайте его командой `git add -N tpws/udp.c tpws/udp.h tpws/quicfake.c tpws/quicfake.h && git diff -- 'tpws/*.c' 'tpws/*.h' tpws/Makefile > tpws-socks-udp.patch`.
